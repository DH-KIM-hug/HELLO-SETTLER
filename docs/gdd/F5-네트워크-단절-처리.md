# F5 네트워크 단절 처리

> 2026-11-16 · 확정 (위임 결정 1·2 반영). MVP에서 네트워크를 쓰는 기능은 **날씨 조회 하나**뿐이다. 클라우드 저장(0.5)과 결제·광고(0.9)는 X6·X8에서 서버 구조와 함께 정한다 (책 범위 밖, 별도 정의).

## 기능별 표

| 기능 | 네트워크 | 오프라인일 때 |
|---|---|---|
| 놓기, 방문, 선물, 상점, 도감, 사진, 저장 | 필요 없음 | 그대로 됨 |
| **날씨 조회 (S1)** | 있으면 사용 | 대체 날씨 (캐시 → 날짜 시드). 게임은 그대로 된다 |
| (0.5) 클라우드 저장 | 필요 | 기기 저장만 하고, 연결되면 올림 `[X8]` |
| (0.9) 광고 보상 · 유료 재화 | 필요 | 버튼을 흐리게 표시, "연결되면 다시" `[X6]` |

## 날씨 조회 상태 구분

| 결과 | 판단 | 처리 |
|---|---|---|
| Ok | 응답 정상, 날씨 코드 해석 성공 | 캐시 갱신 (`fetched_at`, state) → `env_changed` |
| Disconnected | 연결 없음 | 캐시가 유효 시간(`weather_cache_ttl_s`, TEMP 3시간) 안이면 캐시, 아니면 시드 날씨 |
| Timeout | 10초 안에 응답 없음 | Disconnected와 같음. 다음 간격에 다시 시도 |
| ServerError (5xx) · 해석 실패 | 서비스 문제 | 같음 + 개발 로그 |
| Unauthorized / 차단 (4xx) | 약관·키 문제 | 같음 + 하루 동안 다시 시도하지 않음 + 개발 로그 |
| 위치 권한 없음 | - | 조회하지 않음. 시드 날씨 |

**Unknown 상태:** 요청을 보냈는데 앱이 백그라운드로 가서 결과를 모르는 경우. 날씨 조회는 읽기 전용이라 결과를 버리고, 다음에 다시 조회한다.

## 재시도
- 날씨 조회는 **읽기**이므로 안전하게 다시 시도할 수 있다.
- 간격: 앱을 열 때 + 열려 있는 동안 `weather_refresh_s`(TEMP 30분)마다.
- 실패 후 재시도 간격: 1분 → 5분 → 30분 (최대).

## 멱등성
- 날씨 조회는 아무것도 쓰지 않으므로 멱등이다.
- 쓰기 요청(0.5 클라우드, 0.9 결제)에는 `request_id`를 붙여 서버에서 중복을 막는다 `[X8]`.

## Source of Truth
- **날씨:** 외부 서비스가 원본이다. 게임은 해석한 3종(맑음, 흐림, 비)만 쓴다.
- **방문 판정:** 판정 시점의 S1 값을 쓴다. 조회 응답이 늦게 도착하면 **다음 판정부터** 적용하고, 지난 판정은 다시 하지 않는다.

## 통신 성공 ≠ 기능 성공
HTTP 200이어도 날씨 코드를 해석하지 못하면 실패로 본다.

## 로딩 해제 보장
- 날씨 조회 때문에 화면을 막지 않는다. 뒤에서 조회한다.
- P0의 2초 상한은 날씨 응답을 기다리지 않는다.

## 개인정보
- 서비스에는 대략 좌표(소수 1자리)만 보낸다.
- 이메일, 기기 ID 같은 다른 정보는 보내지 않는다.
- 요청 헤더에 사용자 식별 정보를 넣지 않는다.
